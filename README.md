# Payer AI Assistant on Retell AI (proof of concept)

A working local prototype of a member services and provider services AI assistant for health plans, built on Retell AI. It covers voice over the phone, voice in the browser, and web chat, all backed by one middleware that talks to the payer's core system (TriZetto FACETS, mocked here).

All data in this repository is synthetic. Do not load real PHI into it.

```
 Member / provider                                  Retell AI cloud
 ┌──────────────┐  web chat + web voice  ┌──────────────────────────────┐
 │ Payer portal │ ─────────────────────► │ Voice / chat agents (LLM)     │
 │  + widget    │◄─── identity token ─┐  └───────┬───────────▲──────────┘
 └──────────────┘                     │  tools, │ inbound   │ create-web-call,
 ┌──────────────┐   PSTN / SIP        │  webhooks (signed)  │ create-chat
 │  Phone call  │ ─────► Retell ──────┼──────────▼──────────┴──────────┐
 └──────────────┘                     │  ┌────────────────────────────┐ │
                                      └─►│ middleware (FastAPI)       │ │
 ┌──────────────┐  admin API (token)     │  inbound context, tools,   │◄┘
 │ Admin console│ ─────────────────────► │  webhook, widget, admin    │
 └──────────────┘                        └──────┬──────────────┬──────┘
                                                │              │ X-Gateway-Key (+ mTLS in prod)
                                         ┌──────▼─────┐  ┌─────▼──────────────┐
                                         │ PostgreSQL │  │ FACETS gateway     │
                                         │ RLS by org │  │ (mock-facets here) │
                                         └────────────┘  └────────────────────┘
```

## What's in the box

| Path | What it is |
| --- | --- |
| `middleware/` | FastAPI service. Retell inbound-call webhook, 8 mid-call tools, post-call webhook, widget API, admin API. 12 tests. |
| `mock-facets/` | Mock FACETS gateway with sample members, providers, claims, accumulators, benefit rules and prior auths. |
| `frontend/` | React + TypeScript + Tailwind (shadcn-style components). Admin console, a demo payer portal, and the embeddable widget built as one script. |
| `retell/prompts/` | System prompts for the member services and provider services agents. |
| `retell/generated/` | Full Retell LLM + agent configs (tools, transfer, PII scrubbing, post-call analysis), regenerated by the provisioning script. |
| `scripts/provision_retell.py` | Creates the LLMs, voice agents and chat agents in your Retell workspace and binds phone numbers. |
| `scripts/simulate_call.py` | Replays signed Retell traffic for four call scenarios, so you can test without Retell or a phone. |
| `db/init.sh` | Creates the non-superuser app role (needed for row-level security to apply). |
| `docker-compose.yml` | Postgres, mock FACETS, middleware and frontend. |

## Quick start (no Retell account needed)

```bash
cp .env.example .env          # set the passwords and tokens; keep ALLOW_UNSIGNED_RETELL=true for now
docker compose up -d --build
python3 -m pip install httpx && python3 scripts/simulate_call.py   # replays 4 phone calls
```

Then open:

- Admin console: http://localhost:8080/admin (sign in with `ADMIN_API_TOKEN`)
- Demo payer portal with the widget: http://localhost:8080/portal. Switch between two members and two provider offices; chat works in demo mode with a keyword-routed stand-in that calls the same backend tools the real agent uses.
- Plain-HTML embed example: http://localhost:8080/embed-example.html

Frontend dev server instead of nginx: `cd frontend && npm ci && npm run dev` (http://localhost:5173, proxies `/api` to port 8000).

## Connecting Retell

1. Expose the middleware over HTTPS: `ngrok http 8000` or `cloudflared tunnel --url http://localhost:8000`.
2. Put your Retell API key in `.env` as `RETELL_API_KEY` and set `ALLOW_UNSIGNED_RETELL=false`.
3. Create the agents:
   ```bash
   RETELL_API_KEY=key_... python3 scripts/provision_retell.py --base-url https://<tunnel> \
     --member-number +1XXXXXXXXXX --provider-number +1XXXXXXXXXX   # numbers are optional
   ```
   It prints four agent IDs; add them to `.env` and `docker compose up -d middleware`.
   Use `--dry-run` to only write `retell/generated/*.json` if you'd rather paste into the dashboard.
4. Test: call the member number from a phone listed in `mock-facets/mock_facets/data.py` (or any phone and give member ID `MEM-987654`, DOB March 12 1984), or use the portal's Talk tab.

Sample data to try: members `MEM-987654` (Sarah, PPO, DOB 1984-03-12), `MEM-445566` (Miguel, HMO, DOB 1979-11-02), `MEM-778899` (terminated coverage, DOB 1991-06-25); providers NPI `1234567893` / TIN `998877665` and NPI `1987654320` / TIN `112233445`; claims `CLM-112233` (denied duplicate), `CLM-112200` (paid), `CLM-334455` (pended), `CLM-556677` (denied, no prior auth), `CLM-667788` (paid); CPT codes 99213, 99214, 70553, 73721, 27447, 97110, 90834.

## How the HIPAA-minded design works

- **Every Retell request is verified.** Inbound, tool and webhook endpoints check `X-Retell-Signature` (`v=<ms>,d=HMAC-SHA256(api_key, raw_body + ms)`, 5-minute replay window), the same algorithm as Retell's SDK `verify()`. Retell's published egress IP (`100.20.5.228`) can be allowlisted on top at the load balancer.
- **Nothing sensitive is in the prompt before verification.** The inbound webhook returns only plan name, greeting, hours and flags. Caller ID can match a member, but it's only a hint: the caller still has to give their date of birth.
- **Tools enforce identity and ownership server-side**, not in the prompt. Unverified callers get nothing but verification. Members see only their own records; providers see only claims under their own tax ID, and must give a patient's member ID and DOB for every patient lookup. A claim that belongs to someone else returns the same "not found" as a claim that doesn't exist. Three failed verifications lock the conversation.
- **Web sessions start verified** from the payer portal's signed, 15-minute identity token. The browser never sees the Retell API key and can't choose the agent or caller identity: the middleware creates the web call or chat itself.
- **Redaction before storage.** Transcripts and summaries are scrubbed (SSNs, card numbers, emails, and dates the caller speaks) before they reach Postgres; the agents also have Retell's post-call PII scrubbing and `everything_except_pii` storage turned on.
- **Row-level security.** Every table carries `payer_organization_id`, with forced RLS policies; the app connects as a non-superuser and sets the org on each transaction. Verified: the app role sees 0 rows without the setting and 0 rows for another org.
- **Audit trail** of every tool call (latency, outcome, arguments with DOB masked), webhook, config change and transcript view.
- **No FACETS data at rest.** Only identifiers and redacted transcripts are stored; plan data is fetched per request and discarded.
- **Human handoff** is a Retell warm transfer to the number set in Agent settings, with a whispered summary for the representative that excludes DOB and SSN.

## API surface

| Endpoint | Caller | Purpose |
| --- | --- | --- |
| `POST /api/v1/retell/inbound` | Retell (phone number `inbound_webhook_url`) | Returns `call_inbound.dynamic_variables` and `metadata` |
| `POST /api/v1/retell/tools/{name}` | Retell custom functions | `verify_member_identity`, `verify_provider_identity`, `get_coverage_and_accumulators`, `check_member_eligibility`, `check_claim_status`, `check_procedure_coverage`, `get_prior_authorizations`, `create_service_request` |
| `POST /api/v1/retell/webhook` | Retell agent `webhook_url` | `call_started/ended/analyzed`, `transfer_*`, `chat_*` events |
| `GET /api/v1/widget/config`, `POST /api/v1/widget/voice/v3/create-web-call`, `POST /api/v1/widget/chat/...` | Widget (portal token) | Start web voice, start/send/end chat |
| `GET /api/v1/admin/stats`, `/calls`, `/calls/{id}`, `/audit`, `GET/PUT /agent-config` | Admin console (admin token) | Dashboard data and no-code settings |
| `GET /api/v1/demo/personas`, `POST /api/v1/demo/portal-token` | Demo portal (only with `DEMO_MODE=true`) | Stands in for the payer portal signing identity tokens |

Interactive docs at http://localhost:8000/docs.

## Embedding the widget on a payer site

```html
<script src="https://<your-host>/widget/payer-assistant.js"></script>
<script>
  PayerAssistant.mount({
    apiBase: "https://<middleware-host>",
    getPortalToken: () => fetch("/portal/ai-token").then(r => r.text()), // portal backend signs this
  });
</script>
```

The portal's backend signs an HS256 JWT with `PORTAL_JWT_SECRET`, audience `payer-ai-widget`, and claims `sub`, `persona` (`member` or `provider`), `member_id` or `provider_npi` + `provider_tax_id`, and optional `name`. The widget renders in a shadow root so the portal's CSS can't affect it.

## Where this differs from the original research notes

Checked against Retell's docs and SDKs (retell-sdk 6.0.1, retell-client-js-sdk 3.0.2) in October 2026:

- The inbound webhook body is `{"event": "call_inbound", "call_inbound": {call_id, agent_id, from_number, to_number, ...}}`, and the response must be wrapped as `{"call_inbound": {"dynamic_variables": ..., "metadata": ..., "override_agent_id": ...}}`. There is no `current_prompt_override`; per-call context goes in through dynamic variables referenced in the prompt (`{{first_name}}`) or `agent_override`.
- Retell authenticates its requests with the `X-Retell-Signature` HMAC described above, not an `X-Retell-API-Key` header.
- Custom tools are called with `POST {name, call, args}`, so the tool endpoints are POST rather than GET with query parameters.
- Web calls are created with `POST /v3/create-web-call`. The browser SDK's `RetellWebClient.startCall` is deprecated in favour of `RetellClient.createWebCall`, which this widget uses with a server-side proxy.
- Dynamic variable values must be strings.

## Not production-ready yet

This proves out the integration pattern. Before real PHI:

- **Contracts:** BAAs with Retell, your cloud provider and every sub-processor; BAA with each payer.
- **Identity:** OIDC SSO (Okta / Ping / Entra ID) with roles for the admin console instead of a shared token; asymmetric (RS256/JWKS) portal tokens instead of a shared HS256 secret.
- **Infrastructure:** single-tenant VPC per enterprise payer, private subnets, KMS encryption with customer-managed keys, TLS everywhere, mTLS to the payer gateway (`FACETS_CLIENT_CERT`/`KEY` are wired but unused locally), WAF and IP allowlisting in front of the Retell endpoints, Secrets Manager instead of `.env`.
- **Data:** immutable audit storage (S3 Object Lock / CloudTrail), retention policies, signed short-lived URLs if call recordings are surfaced, a reviewed redaction policy.
- **Integrations:** the real FACETS gateway contract (and HealthEdge HRWS, FHIR Patient Access, X12 270/271 and 276/277 adapters behind the same interface in `middleware/app/services/facets.py`), CRM write-back (Salesforce Health Cloud Case/Task, Dynamics 365, Pega), SIP trunking to the payer's contact center.
- **Operations:** migrations (Alembic) instead of `create_all`, rate limiting, monitoring and alerting, load testing, SOC 2 Type II and a HITRUST roadmap.
- **Product:** clinical and compliance review of the prompts, appeals and grievance routing rules, Spanish and other languages, accessibility review of the widget, splitting the voice SDK so the widget bundle is smaller (it's ~800 KB today because of the WebRTC client).
